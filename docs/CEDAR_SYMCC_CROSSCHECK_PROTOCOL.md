# Protocol: SymCC's check of the Cedar exact study's equivalence verdicts

This protocol was written before the study it describes computed any outcome, and
`scripts/cedar_symcc_crosscheck.py` refuses to run on the population below unless this file
hashes to the value fixed in the script. Like the paper's other protocols, it is a hash the
authors recorded in the same working session, not an externally timestamped registration; the
commit that adds it precedes the commit that adds the study's results. The schemas were found,
and the files they admit fixed, before SymCC was run on any of the study's mutants: that list is
`docs/cedar-schema-candidates-v1.json`, whose SHA-256 (line endings normalised to LF) is
`e7b0954e645117a2e21dd6fff65f196b31c715b144fd940564e88049f0720436`, and this file fixes it by
that hash.

## Why

The Cedar exact study (`docs/EXACT_EVALUATION_PROTOCOL_CEDAR.md`, artifact
`docs/cedar-suite-strategy-study-v1.json`) calls a mutant *equivalent* when no cell of its
file's witness space separates it from the file, and checks that the witness space is complete
by drawing 200 requests per file. A drawn sample can miss the one request that separates. This
study puts the same question to an independent decision procedure: SymCC, Cedar's symbolic
compiler, which reduces equivalence of two policy sets to a satisfiability query that a solver
decides.

## What it can and cannot show

SymCC decides equivalence over the requests and entity stores a schema admits, one request
environment -- a principal type, an action and a resource type -- at a time. The study's verdict
of equivalent is a claim about every request. The check is therefore one-directional: a
counterexample that the study's own engine confirms refutes the verdict, while a verified
equivalence does not confirm it beyond the requests the schema admits. This project writes no
schema; a file is checked only under a schema its own authors wrote.

## Tools

- `cedar-policy-cli` 4.12.0, the experimental build from the Cedar project's release
  `cedar-policy-cli-v4.12.0`, whose `symcc` command runs the `cedar-policy-symcc` analyses. The
  study runs on Windows x86-64 from `cedar-policy-cli-experimental-x86_64-pc-windows-msvc.zip`
  (SHA-256 `8a2f9746ccf5d88bacfc81487d163cdb32d258df9ec23ca5d4f917438774b853`); the same
  release's Linux build is `cedar-policy-cli-experimental-x86_64-unknown-linux-gnu.tar.xz`
  (SHA-256 `bb991fe1fc25b24d1a1cd1b78266950e8d33015eb818acabe297365bc4905392`).
- cvc5 1.3.1, static build (`cvc5-Win64-x86_64-static.zip`, SHA-256
  `e1e183f50f1bbd9d10b2dc6ab9574cb9fa02acfdc1957f43040db3529f92b94e`), which the CLI starts with
  a limit of 60 seconds per query (`--tlimit=60000`).
- The study's engine, `cedarpy` 4.12.1, for every replay; its version must equal the one the
  Cedar artifact records.

## Population

**Files.** The 153 files the Cedar exact study scored.

**Schemas.** For each file, `scripts/cedar_schema_candidates.py` listed the schema candidates in
the file's repository at the commit the corpus records: every `*.cedarschema` or
`*.cedarschema.json` file, and every `.json` or `.cedar` file whose name contains "schema". They
are taken nearest first: the file's own directory, then its ancestors from the nearest, then the
rest of the repository, by path within each group. The file's schema is the first candidate
under which `cedar validate --validation-mode strict` accepts the file; a JSON candidate that
wraps its schema as `{"cedarJson": "..."}`, the form Amazon Verified Permissions exports, is
read unwrapped. 109 files have a candidate and 72 files in 53 repositories have a schema: 41 in
the file's own directory, 18 in an ancestor and 13 elsewhere in the repository. The data file
lists every candidate tried and why each one before the schema was passed over.

**Environments.** Every (principal type, action, resource type) the schema's actions apply to,
in the order the schema declares them: 1,718 in all, from 1 to 174 per file.

**Mutants.** The study's mutants of each file, regenerated by the study's own code. Outside
development, the 71 files hold 173 equivalent verdicts, in 32 files, and 830 live verdicts, over
1,715 environments.

**Development.** SymCC was run before this protocol on one population file,
`Anumehajain78/promptfence/backend/policies/forbid-support-delete.cedar`, to learn the command's
output: the file against itself, against a copy with its policy's id changed, and against a
hand-made copy with its effect flipped, in each of its three environments. It holds 7 equivalent
verdicts and 1 live one; it is checked like the others, reported and flagged, and not pooled. A
synthetic schema and policy written for the purpose, outside the population, fixed the format of
a counterexample.

## Procedure

1. **Reproduce the verdicts.** Convert the file to Cedar's JSON form with cedarpy, as the study
   did, and regenerate its analysis with the study's own function and seed (`analyse_file`, with
   `random.Random(f"20261003:{subject}")`). The counts of equivalent, live and unrunnable
   mutants must equal the artifact's. A file where they differ is excluded as *verdicts not
   reproduced*, which is a finding about the study and is reported as one.
2. **Control.** In every environment, SymCC compares the file's own text with its JSON form;
   each comparison must be verified. An environment where the file's text does not compile is
   *unusable* and is reported; a file with no usable environment is excluded as *SymCC does not
   compile it*. A file whose text and JSON form differ in some environment is excluded as *JSON
   form not faithful* and reported as a finding.
3. **Check.** Each mutant, in the JSON form the study evaluated, is compared with the file's
   JSON form in each usable environment by `cedar symcc --principal-type P --action A
   --resource-type R --schema S --schema-format F --counterexample equivalent --policies1
   file.json --policies1-format json --policies2 mutant.json --policies2-format json`. An
   environment's result is one of: *verified*; *counterexample*; *mutant does not compile*, when
   the mutant is not well typed there; *no answer*, for the solver's limit or any other failure;
   and *wall-clock limit*, when the process is stopped after 600 seconds. Equivalent verdicts
   are checked in every usable environment. Live verdicts are checked in the environments' order
   until a counterexample is confirmed.
4. **Replay.** Every counterexample is parsed -- the request, its context, and each entity's
   ancestors, attributes and tags -- and decided by cedarpy, through the study's own evaluation
   function, for the file's and the mutant's JSON forms. It is *confirmed* when the two
   decisions differ and *unconfirmed* when they do not. It is *unreplayed* when its text cannot
   be read, for example a value printed as `<unknown>`, and that text is kept in the artifact.

## Outcomes

Each equivalent verdict is one of: *refuted*, with a confirmed counterexample in some
environment; *not refuted, every environment verified*; *not refuted, partly checked*, with no
confirmed counterexample, at least one environment verified, and some environment with another
result; or *unchecked*, with no environment verified and none refuting. Unconfirmed and
unreplayed counterexamples never refute; they are counted and listed.

**Primary.** The number of the study's equivalent verdicts that are refuted, out of the
equivalent verdicts of the files outside development, with the counts of the other three
classes. The prediction is zero. Each refutation is reported with its file, mutant, environment
and request. It is flagged when the request's principal is its resource, because the study's
witness space omits such requests by construction (`request_of`), which its protocol does not
state.

**Secondary, descriptive.**
1. The live verdicts: how many are confirmed live under the schema, and how many SymCC finds
   equivalent in every usable environment. The second kind are mutants that the study kills only
   with requests the authors' schema rules out. Their share, and the operators that make them,
   show how far the score depends on the requests counted, as the Rego scores depend on the
   parameter settings a suite tests; they are not errors.
2. SymCC's agreement with the engine: the confirmed, unconfirmed and unreplayed counterexamples
   over every mutant checked.
3. The control's results, by file.

There is no hypothesis test; the outcomes are counts.

## What follows from the result

Results are reported as found. A defect that the check reveals in the witness construction is
not repaired under this protocol: correcting it would make a new version of the Cedar exact
study, under a new protocol, and this study's artifact records the verdicts of the committed
version. Any deviation from this protocol is recorded in the artifact.
