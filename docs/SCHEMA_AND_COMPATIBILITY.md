# Schemas and Compatibility

## Compatibility promise

TrustWeave treats manifests, policies, scenarios, bundles, trace inputs, reviews, and attestations as evidence contracts. A change to one of these formats can alter a CI result or a reviewer’s conclusion. For that reason, the repository uses explicit schema-version strings and a conservative evolution policy.

The current formats are pre-release `v1alpha1` contracts. They are stable enough for the checked-in examples and CI, but a future stable release may change them with documented migration guidance.

| Artifact | Current schema version | Structural schema |
|---|---|---|
| Agent manifest | `trustweave.dev/v1alpha1` | [`schemas/agent-manifest.schema.json`](../schemas/agent-manifest.schema.json) |
| Deterministic policy | `trustweave.dev/v1alpha1` | [`schemas/policy.schema.json`](../schemas/policy.schema.json) |
| Local trace | `trustweave.dev/trace/v1alpha1` | [`schemas/trace.schema.json`](../schemas/trace.schema.json) |
| MCP metadata profile | `trustweave.dev/mcp-profile/v1alpha1` | [`schemas/mcp-profile.schema.json`](../schemas/mcp-profile.schema.json) |
| Local attestation | `trustweave.dev/attestation/v1alpha2` | Generated by the typed core; the verifier remains compatible with local `v1alpha1` statements. |
| Local SARIF evidence | SARIF `2.1.0` | OASIS SARIF standard; derived from local review artifacts only. |
| Agent Security Bundle | `trustweave.dev/bundle/v1alpha1` | Generated by the typed core; no separate JSON Schema yet. |
| Bundle diff | `trustweave.dev/bundle-diff/v1alpha1` | Generated by the typed core; no separate JSON Schema yet. |
| Policy review | `trustweave.dev/policy-review/v1alpha1` | Generated by the typed core; no separate JSON Schema yet. |
| Trace review | `trustweave.dev/trace-review/v1alpha1` | Generated by the typed core; no separate JSON Schema yet. |

## Two validation layers

TrustWeave deliberately uses two layers of validation.

1. **JSON Schema** gives editors and external tooling structural feedback for manifest, policy, trace, and MCP-profile documents.
2. **The typed Python validator** is authoritative at runtime. It rejects unknown fields by default and enforces semantic checks such as unique names, valid trust labels, valid action classes, known manifest references, non-empty required values, and trace-name consistency.

CI validates every checked-in contract example against its published schema and then through its typed parser. This detects structural drift without adding a required runtime JSON Schema dependency. Read [ADR-0001](ADR-0001-TYPED-PARSER_AUTHORITY.md) for the decision, scope, and opaque-metadata boundary.

Do not assume the structural schemas encode every Python rule. When changing an input contract, update both layers and add a regression test that demonstrates the intended relationship.

## Allowed additive changes

A pre-release-compatible addition should meet all of the following conditions:

| Condition | Required evidence |
|---|---|
| Existing versioned examples still parse and produce the same deterministic decisions. | Regression test and CI artifact. |
| New behavior has an explicit default or rejects incomplete input safely. | Validator test for the default or rejection path. |
| Reports clearly state any new review boundary or limit. | Documentation update and report snapshot assertion where appropriate. |
| Existing generated artifacts remain readable by the current CLI. | Compatibility test or documented migration. |
| A derived SARIF result has stable ordering and fingerprints for unchanged local review artifacts. | Deterministic SARIF unit test and CI artifact assertion. |

Examples include a new optional descriptive field that the runtime ignores safely, or a new additive report field with a documented default. The optional policy `approval_control` object follows this rule: policies without it remain valid, but `policy-check` emits `TW-POL-004` when a sensitive/external `require_approval` path lacks the declaration. When supplied, its `mechanism`, unique `binds_to` values, and boolean `fail_closed` field are validated by both the schema and typed parser.

## Breaking changes

The following changes require a new schema version and a migration note:

- Renaming or removing a required field.
- Changing a valid trust label, action class, decision, or command exit-code meaning.
- Changing first-match policy semantics.
- Changing the canonical identity of a source, tool, flow, MCP profile tool mapping, or review identifier.
- Changing an artifact digest, attestation-chain, or review-finding identifier in a way that invalidates stored evidence.
- Changing the privacy boundary by adding message or tool-argument content to a trace-review artifact.

A breaking change must update the changelog, release notes, examples, schemas, typed validator, tests, CLI reference, and relevant threat-model or quality documentation.

## Attestation migration

New local attestations use `trustweave.dev/attestation/v1alpha2`. Their integrity chain hashes canonical stable bundle and test-result payloads after excluding volatile `generated_at` metadata; exact file hashes remain in the predicate and subject for local file identification. This distinguishes reproducible evidence content from time-varying provenance.

The verifier accepts both `v1alpha1` and `v1alpha2` local statements. Existing `v1alpha1` statements retain their original file-hash chain semantics. Regenerate an attestation after regenerating its local bundle and test-result artifacts to adopt `v1alpha2`; no remote migration is performed.

The distributed package includes `py.typed` as PEP 561 package data. Downstream type consumers can therefore use the typed public modules installed from the wheel.

## Stable review identifiers

`TW-POL-*`, `TW-DIFF-*`, `TW-TRACE-*`, and `TW-MCP-*` identifiers are part of the review contract. Do not reuse an identifier for a different condition. If a condition changes materially, introduce a new identifier and document the migration impact.

## Contract change checklist

Before merging an input or output contract change, confirm all statements below.

- [ ] The new or changed behavior is covered by a deterministic positive, negative, or boundary test.
- [ ] Existing reference manifests, policies, scenarios, traces, and generated workflows still pass or have a documented migration.
- [ ] JSON Schema and typed runtime behavior are intentionally aligned or their difference is documented; checked-in examples validate through both layers.
- [ ] The CLI reference states updated inputs, outputs, and exit-code behavior.
- [ ] The threat model and quality guide state any new security or privacy boundary.
- [ ] The changelog explains compatibility and migration impact.
- [ ] New approval-control declarations are limited to documented evidence metadata and do not imply runtime approval enforcement.
